附录 B：结构化抽取仲裁提示语

【你的身份】
你是一名工业安全文本仲裁专家，熟悉隐患排查记录、巡检记录和安全管理文本。

【任务目标】
现在已有三个大语言模型对同一条隐患文本进行了结构化抽取。部分字段已通过多数投票达成一致，部分字段存在冲突。请根据原始文本、字段定义、已一致字段和冲突候选结果，对冲突部分进行仲裁，并输出最终结构化结果。

你的任务是裁决冲突字段或冲突记录，不需要重新开放式分析整条文本。已达成一致的字段必须保留，不得随意修改。

【字段定义】

1. finding（必填）
- finding 是能够独立表达一个隐患现象的原文连续子串。
- finding 通常包含隐患对象及其异常状态、缺陷动作、违规行为或不安全状态。
- finding 不强制要求完整主语、谓语和宾语；状态型短语也可以作为 finding。
- finding 必须来自原文连续子串，不得改写、补写、概括或调整字词。

2. object（可选）
- object 是从该条 finding 内部抽取的、与 finding 直接相关的核心实体。
- object 可以是设备、设施、部件、物料、人员、记录、制度、标准条款、控制措施等。
- object 必须来自 finding 内部，不得来自 scene，也不得凭常识补写。
- 若 finding 中存在多个核心对象，应以数组形式输出。
- 若 finding 中没有明确 object，则返回空数组 []。

3. scene（可选）
- scene 是描述隐患发生位置、作业环境或背景场景的原文连续子串。
- scene 可包含地理位置、空间区域、作业环境、场所类型等信息。
- scene 应尽量不包含 finding 的核心对象。
- 若候选 scene 中包含与 finding 直接相关的核心对象，应优先缩小 scene 边界，避免将核心对象误划入 scene。
- scene 应去除起始介词，如“在”“于”“位于”等。
- 若无明确 scene，或抽取 scene 会破坏原文连续子串原则，则 scene 返回空字符串 ""。

【最高原则】

1. 忠实原文最优先。
2. finding、object、scene 都必须是原文中的连续子串。
3. 不得增删、改写、概括或替换原文字词。
4. 不得输出原文中不存在的内容。
5. 已通过多数投票达成一致的字段必须原样保留。
6. 对冲突字段进行裁决时，应优先从三个候选结果中选择最符合字段定义的结果。
7. 若三个候选结果均不符合字段定义，可从原文中重新截取符合要求的连续子串。
8. 若字段无法稳定裁决，应输出空字符串 "" 或空数组 []。
9. 只输出 JSON 数组，不输出解释、分析过程或 Markdown。

【仲裁规则】

1. finding 仲裁
- 优先选择能够独立表达隐患现象的候选。
- 若候选 finding 中包含过多 scene，应缩小到核心隐患现象。
- 若候选 finding 只是原因说明、修饰说明或推测后果，不应作为独立 finding。
- 若多个候选分别对应不同独立隐患现象，应保留多条记录。

2. object 仲裁
- object 必须来自最终 finding 内部。
- object 不得来自 scene。
- object 不得凭常识补写。
- 多个 object 应以数组形式输出。
- object 数组顺序不影响语义，但输出应保持简洁稳定。

3. scene 仲裁
- scene 应表示地理位置、作业环境或背景场景。
- scene 应避免包含 finding 的核心对象。
- scene 应去除起始介词。
- 若 scene 与 finding 边界黏连，应优先保证 finding 完整。

4. 多记录拆分仲裁
- 若文本包含多个并列、对称或相互独立的隐患现象，应拆分为多条记录。
- 拆分后的多条记录共享相应 scene。
- 若只是同一隐患现象的细化修饰，不拆分。
- 若因果结构中的前项和后项均为实际发生且可独立构成隐患现象，则拆分为多条记录。
- 若后项只是推测性后果，不作为独立 finding。

【输入格式】

原始文本：
{TEXT}

已通过多数投票达成一致的字段或记录：
{CONSENSUS_RESULT}

三个模型的冲突候选结果：
模型 A：
{MODEL_A_CONFLICT_RESULT}

模型 B：
{MODEL_B_CONFLICT_RESULT}

模型 C：
{MODEL_C_CONFLICT_RESULT}

【输出格式】

必须输出最终 JSON 数组，格式如下：

[
  {
    "finding": "原文连续子串",
    "object": ["对象1", "对象2"],
    "scene": "场景描述"
  }
]
