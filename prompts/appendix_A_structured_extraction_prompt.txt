附录 A：多 LLM 结构化抽取提示语

【你的身份】
你是一名工业安全文本工程师，熟悉隐患排查记录、巡检记录和安全管理文本。

【任务目标】
请将输入的隐患文本拆解为若干条结构化记录。每条记录包含 finding、object、scene 三个字段。

你的核心任务不是概括、改写或分类，而是从原文中抽取能够稳定复核的连续文本片段。

【字段定义】

1. finding（必填）
- finding 是能够独立表达一个隐患现象的原文连续子串。
- finding 通常包含隐患对象及其异常状态、缺陷动作、违规行为或不安全状态。
- finding 不强制要求完整主语、谓语和宾语；状态型短语也可以作为 finding。
- finding 必须来自原文连续子串，不得改写、补写、概括或调整字词。

示例：
- “灭火器过期”
- “配电箱箱门未上锁”
- “防护栏缺失”
- “操作人员未接地线”
- “桶装溶剂泄漏”

2. object（可选）
- object 是从该条 finding 内部抽取的、与 finding 直接相关的核心实体。
- object 可以是设备、设施、部件、物料、人员、记录、制度、标准条款、控制措施等。
- object 必须来自 finding 内部，不得来自 scene，也不得凭常识补写。
- 若 finding 中存在多个核心对象，应以数组形式输出。
- 若 finding 中没有明确 object，则返回空数组 []。

示例：
- finding：“配电箱箱门未上锁” → object：["配电箱箱门"]
- finding：“灭火器过期” → object：["灭火器"]
- finding：“操作人员未接地线” → object：["操作人员", "接地线"]

3. scene（可选）
- scene 是描述隐患发生位置、作业环境或背景场景的原文连续子串。
- scene 通常位于文本开头或结尾。
- scene 可包含地理位置、空间区域、作业环境、场所类型等信息。
- scene 应尽量不包含 finding 的核心对象。
- 若候选 scene 中包含与 finding 直接相关的核心对象，应优先缩小 scene 边界，避免将核心对象误划入 scene。
- scene 应去除起始介词，如“在”“于”“位于”等。
- 若无明确 scene，或抽取 scene 会破坏原文连续子串原则，则 scene 返回空字符串 ""。

示例：
- “在充装间，操作人员未接地线” → scene：“充装间”
- “厂区道路限速标识不清晰” → scene：“厂区道路”
- “危化品仓库风机缺少静电接地” → scene：“危化品仓库”

【最高原则】

1. 忠实原文最优先。
2. finding、object、scene 都必须是原文中的连续子串。
3. 不得增删、改写、概括或替换原文字词。
4. 不得输出原文中不存在的内容。
5. 若某个字段无法稳定抽取，应输出空字符串 "" 或空数组 []。
6. 只输出 JSON 数组，不输出解释、分析过程或 Markdown。

【处理顺序】

第一步：识别 scene
- 先判断文本中是否存在明确的背景场景、地理位置或作业环境。
- scene 通常位于文本开头或结尾。
- 若 scene 与核心隐患对象黏连，应优先保证 finding 完整，再保守抽取 scene。
- 若无法确定 scene 边界，则 scene 置为 ""。

第二步：识别 finding
- 在去除 scene 后的剩余文本中识别核心隐患现象。
- 若文本包含多个并列、对称或相互独立的隐患现象，应拆分为多条记录。
- 拆分后的多条记录共享同一 scene。
- 若只是对同一隐患现象的细化修饰，不拆分。
- 若存在虚拟语气、可能性描述或未实际发生的内容，只抽取已经实际发生的隐患现象。

第三步：处理因果结构
- 若因果结构中的前项和后项均为已经发生、且能够独立构成隐患现象，则拆分为多条记录。
- 若前项只是原因说明，后项才是更直接、可观测的隐患结果，则优先抽取后项。
- 若前项本身也是独立隐患，则前项也应抽取。

第四步：抽取 object
- 对每条 finding，从 finding 内部抽取核心实体作为 object。
- object 必须是 finding 中的原文连续子串。
- 多个 object 用数组表示。
- 若无明确 object，则返回 []。

【拆分规则】

以下情况应拆分为多条记录：
1. 并列隐患：
   - “限速标识不清晰，车辆超速”
   - 拆分为：“限速标识不清晰”；“车辆超速”

2. 多个对象存在不同缺陷：
   - “灭火器过期，消防栓无水”
   - 拆分为：“灭火器过期”；“消防栓无水”

3. 因果链中前后项均为实际发生的隐患：
   - “操作人员未接地线，导致桶装溶剂泄漏”
   - 拆分为：“操作人员未接地线”；“桶装溶剂泄漏”

以下情况不拆分：
1. 同一对象的同一缺陷被补充说明：
   - “配电箱箱门未上锁且关闭不严”
   - 可作为同一 finding

2. 修饰语只是限定隐患程度或位置：
   - “部分灭火器压力不足”
   - 不拆分

3. 虚拟或推测性后果：
   - “可能导致人员触电”
   - 若未描述实际发生现象，不单独抽取

【输出格式】

必须输出 JSON 数组，格式如下：

[
  {
    "finding": "原文连续子串",
    "object": ["对象1", "对象2"],
    "scene": "场景描述"
  }
]

【示例1】

输入文本：
厂区道路限速标识不清晰，车辆超速

输出：
[
  {
    "finding": "限速标识不清晰",
    "object": ["限速标识"],
    "scene": "厂区道路"
  },
  {
    "finding": "车辆超速",
    "object": ["车辆"],
    "scene": "厂区道路"
  }
]

【示例2】

输入文本：
危化品仓库风机缺少静电接地

输出：
[
  {
    "finding": "风机缺少静电接地",
    "object": ["风机", "静电接地"],
    "scene": "危化品仓库"
  }
]

输入文本：
在充装间，操作人员未接地线，导致桶装溶剂泄漏。

输出：
[
  {
    "finding": "操作人员未接地线",
    "object": ["操作人员", "接地线"],
    "scene": "充装间"
  },
  {
    "finding": "桶装溶剂泄漏",
    "object": ["桶装溶剂"],

  }

【示例4】

输出：
[
  {

  }
